# Voice clips — plan

Replace Web Speech announcements with pre-rendered audio clips played through
the same `AudioContext` as the beeps, so announcements come out of whatever
device the beeps do.

## Why

On iOS, `speechSynthesis` is rendered by the system speech service on its own
audio session. Web Audio follows the app's session and therefore the connected
Bluetooth route; speech does not, and lands on the phone speaker. There is no
web API to route it (no `setSinkId` in iOS Safari, no output selection in the
Web Speech API). Observed in the wild with a group: music and beeps on the
speaker, "Work" / "Rest" from the phone in someone's pocket.

Playing announcements as decoded `AudioBuffer`s through the existing
compressor node fixes routing, and brings two things for free:

- **Background survival.** Clips can be pre-scheduled on the audio clock like
  the beeps, so they no longer go silent when rAF is throttled — the
  limitation documented at the top of `src/engine/speech.ts` disappears.
- **A consistent voice** across devices, instead of whatever the browser's
  voice list happens to offer.

## The fixed vocabulary ships in the repo

`Work`, `Rest`, `Get ready` and `Done` are committed MP3s in `src/audio/`,
regenerated by `scripts/build-audio.ps1` (`-Force` to replace existing ones)
whenever the voice, a style or the word list changes. They are precached by
the service worker, so they are present before the first run, cost no request,
and work with no network at all.

This covers more than it sounds like: **no preset has an interval label** —
presets only label blocks and sets, which are never announced — so every
preset in the app announces entirely from these four files. The backend below
exists solely for exercise labels a user typed themselves.

## Architecture (custom labels only)

```
Editor Save ──► POST /api/speech {texts:[…]} ──► for each text:
                                                  hash → clip doc exists? ─ yes ─► done
                                                                          └─ no ─► Azure AI Speech
                                                                                   → store doc
                     ◄── {clips:[{text,key}]} ───┘
Client: GET /api/speech/<key> → decodeAudioData → cache (memory + Cache Storage)
        → schedule on the AudioContext next to the beeps
```

- **TTS**: Azure AI Speech (`Microsoft.CognitiveServices/accounts`, kind
  `SpeechServices`), same subscription and Bicep as the rest, on the **free
  F0 tier**: 0.5M characters/month, and an announcement is ~10 characters.
  Real-time REST synthesis to MP3 (`audio-24khz-48kbitrate-mono-mp3`;
  measured 5–11 KB for a one-word clip) — batch synthesis is not available
  on F0, so it is one request per clip.
- **Voice**: `en-US-AriaNeural`, picked by ear against Ava, Jenny, Sara, Nancy
  and Jane. Expressive style turned out to matter more than timbre, and it
  differs per segment (`mstts:express-as`): **`excited` for work labels**,
  **`shouting` for rests**. Yelling "REST" after a hard interval reads as
  relief rather than instruction, and it matches the countdown ticks that now
  pitch *down* into a rest. Voice and style are both part of the clip key, so
  changing either is safe — old clips are simply never requested again.
  - F0's binding limit is **20 requests per 60 seconds**, not adjustable. With
    background generation, dedup and retry that is ample, but 429 must be
    handled with backoff (the docs recommend that on any tier) and generation
    must be resumable across saves. Outgrowing it means switching the resource
    to S0 (~$15/1M chars ≈ 100k announcements for $1.50); no code changes.
- **Storage**: the existing Cosmos container, one doc per clip in partition
  `clip#<hash>` with a fixed id — the same point-read shape `ShareDoc`
  already uses for share codes, so the feature adds **no new storage
  resource, no container CORS and no public blob access**. The MP3 rides in
  the doc as base64 (~7–15 KB, against a 2 MB doc limit).
  - A clip is fetched once per device and then lives in Cache Storage
    forever, so proxying bytes through `/api/speech/<key>` costs one function
    invocation per device per clip. If that ever stops being negligible, the
    escape hatch is a Blob Storage container with immutable public URLs;
    the client only knows the key, so nothing else changes.
- **Keys**: `sha256(voiceId + '|' + normalized text)`, normalized by trim,
  whitespace collapse and lowercase — so "Burpees", "burpees " and "BURPEES"
  are one clip. Content addressing makes generation idempotent and shares
  every clip across users, which is the point: the text is what matters.

## API

`POST /api/speech` — anonymous (recipients of a shared workout have no
account), idempotent, safe to retry.

```jsonc
// POST /api/speech — request
{ "texts": ["Work", "Rest", "Burpees", "Wall balls"] }
// response: one entry per text, "pending" = rate-limited, ask again later
{ "clips": [ { "text": "Work", "key": "ab12…", "status": "ready" },
             { "text": "Burpees", "status": "pending" } ] }
```

`GET /api/speech/<key>` returns the MP3 with a long immutable `Cache-Control`.

Both routes are anonymous — recipients of a share code have no account, and on
F0 there is no spend to protect: abuse hits the rate cap, not a bill. Input
limits stay, to keep one caller from eating the 20/minute window: ≤ 40
characters per text, ≤ 20 texts per request, printable characters only.

## Client

- `src/engine/speech.ts` becomes a clip player: resolve text → `AudioBuffer`
  (memory cache → Cache Storage → network), schedule through a new
  `playBuffer(buffer, delay)` in `audio.ts` so it shares the compressor and
  the session's audio route. Session start pre-schedules the whole run's
  announcements next to the beeps.
- **Fallback stays.** Missing clip (offline, generation failed, budget hit)
  → `speechSynthesis` exactly as today. Worse routing beats silence.
- The vocabulary of a workout is what `compile()` can announce: `"Rest"` plus
  each work segment's label (`interval.label` or `"Work"`).

## Generation trigger

Generation runs on **Save in the editor**, on **import of a shared workout**,
and on first load for presets (a no-op once pre-warmed). It never blocks:
Save writes to localStorage and returns immediately, with a non-modal progress
line ("Preparing audio 2/5"). Failures are silent and retried the next time
the workout is opened or run.

Not opt-in, and not conditioned on the announcements toggle — see the
reasoning in CLAUDE.md's decisions log.

## Privacy note

Clips are shared across users and derived from text a user typed. They are
content-addressed and never enumerated, so finding one requires knowing the
text already. Nothing ties a clip to an account.

## Infra changes

- **No resource is created by this repo.** The Speech account is a shared
  account (`mwse-speech` in `rg-common`, alongside `mwse-cosmos`), created by
  hand once and used by several apps. It must be the single-service kind
  `SpeechServices`: the multi-service `AIServices` resource the portal offers
  under "Azure AI services" has no free tier. Azure allows one free account
  per kind per subscription, so one shared Speech account is not just the
  tidy choice, it is the only one — and it leaves the free Vision/Language
  tiers untouched for other apps. `infra/main.bicep` references it with
  `existing` scoped to that resource group and wires `SPEECH_KEY` /
  `SPEECH_REGION` into SWA app settings the way the Cosmos key already is
  (resolved at deploy time via `listKeys`, never in source).
  - Sharing it means sharing its F0 quota: the 0.5M characters/month and the
    20 requests/60s are **per resource**, across every app pointing at it.
    Background generation with backoff degrades gracefully under that; a
    foreground dependency on synthesis would not, which is another reason
    generation never blocks a save.
  - F0 is intended for development and free-tier use. Moving to S0 is a sku
    change on that one shared account, with no code impact here.
- No new API dependency: Cosmos and `fetch` cover it.
- Local dev: `SPEECH_KEY` in `local.settings.json`. Without a key the endpoint
  reports every clip `failed`, so the client exercises its Web Speech fallback
  — which is also the offline path, so it needs the exercise.
